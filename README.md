# bluetime 引擎

蓝调时刻（Blue Hour）评分引擎。输入经纬度与日期，输出：

- 早/晚**蓝调窗口**的起止时刻与窗口时长
- **蓝度指数**（0~100）：天空够不够蓝、够不够纯
- **综合质量分**（0~100）：这次蓝调值不值得专门去拍
- 各因子明细、月相、地形遮挡说明

当前零第三方依赖（纯 Python 标准库），部署简单、启动快。但这**不是硬约束**——后端跑在自建服务器上（没有云函数那种内存/冷启动限制），凡对精度或效果有明显提升的成熟库都可引入。

---

## 快速开始

```bash
cd engine

# 输出文本报告
python -m bluetime.cli --lat 39.9042 --lng 116.4074 --date 2026-10-07

# 输出 JSON（供小程序后端调用）
python -m bluetime.cli --lat 39.9042 --lng 116.4074 --days 3 --json

# 跳过地形遮挡、禁用缓存（离线快速验证）
python -m bluetime.cli --lat 39.9042 --lng 116.4074 --no-terrain --no-cache

# 走「首个访客计算并缓存」策略
python -m bluetime.cli --lat 31.2304 --lng 121.4737 --date 2026-10-08 --day-cache
```

# 单元测试（不联网）
python -m unittest discover -s tests -v

## 核心设计

### 1. 依赖策略：效果优先

现状是**零第三方依赖**（纯标准库）：部署简单、无版本冲突，目前所有本地计算都在毫秒级。

但这**不是硬约束**。早期"必须零依赖"是因为原计划跑在微信云函数（单次运行内存上限 256 MB、冷启动敏感），**现在后端改为自建服务器**（可常驻进程、可装依赖、无 256 MB 限制），原则改为 **效果与精度优先**：任何能明显提升准确度或质量的成熟库都应引入，不再为了"包小"牺牲结果。

### 2. 缓存策略：首个访客计算，其余命中缓存

| 数据类型 | TTL | 理由 |
|---|---|---|
| 地形地平线剖面 | **永久** | 不随时间变化 |
| 当日评分结果 | 1 小时 | 气象预报每 1~6 小时更新，不能永久存 |
| 未来日期结果 | 6 小时 | 远期预报变化更慢 |

并发防护：用 `(scope, key)` 主键 + `status` 标记做**单飞**——同一「城市+日期」同时被多个用户请求时，只有一个真正计算，其余返回 `computing=True`，前端提示"正在计算"并稍后重试。

实测：首次 6.57 s，二次 0.073 s（快约 90 倍）。

存储适配：换 Redis / 数据库时，保持 `(scope, key)` 主键与 `status/expires_at` 语义即可平移。

### 3. 地形遮挡的判据

**关键点**：蓝调时刻太阳本来就位于地平线**以下**（本引擎口径 −5°~−7.5°），所以「太阳是否被地形挡住」是**错误判据**（必然判为全遮挡）。

正确判据是：**朝太阳方向的天空辉光带被地形挡住了多少**。辉光带取地平线以上 0°~25°，地形地平线高度 H 会遮掉最下面的 H 度：

```
terrain_score = clip((band_top - H) / band_top, 0, 1)
```

### 4. 蓝度指数与综合质量分

```
蓝度指数   = 100 × Σ(w · 隶属度)              ← 云/AOD/能见度/臭氧
综合质量分 = 100 × [ 0.70 × 蓝度指数/100
                   + 0.10 × 窗口时长
                   + 0.08 × 地形可见性
                   + 0.06 × 月相
                   + 0.06 × 降水 ]
```

**缺失的因子会被自动剔除并重新归一化权重**，避免"缺数据反而抬高分数"（例如总柱臭氧未接 CAMS 时，不会按 0 分拖低整体）。

### 5. 蓝调 ≠ 晚霞

市面产品（SunsetWx / Sunsethue / GoldCast）评的是日落日出，逻辑是"云能不能接住阳光"；蓝调要的是"天空够不够干净通透"，**云反而是遮挡**。因此本引擎不采用 ray-based 云反射模型。

## 部署（自建服务器）

后端是**自建服务器 + 已 ICP 备案的域名 + HTTPS**（微信小程序 `wx.request` 只能访问已备案的合法域名），**不使用微信云开发 / 云函数**。

1. HTTP 接口层调用 `pipeline.get_or_compute(lat, lon, date)`；
2. 并发已在引擎内保证：`sources.base.fetch_all` 用 `ThreadPoolExecutor` 把「和风气象 / Open-Meteo 气象 / AOD」三路并发发出，串行会明显拖慢响应；
3. `cache.py` 默认 SQLite；多进程部署时换成 Redis（接口签名保持一致）；
4. 首次请求偏慢（要取 4 路外部数据），用「首个访客计算并缓存 + 单飞锁」摊薄，配合前端进度条/倒计时。

## 已知限制

1. **权重是初始估计**，尚未用实测数据标定——这是最大不确定性。
2. **总柱臭氧未接入**（需 CAMS），当前自动剔除该因子并重新归一化；Open-Meteo 的 `ozone` 是表层臭氧，不等于总柱臭氧，未使用。
3. **PVGIS 中国覆盖需实测**，个别点位可能缺失，缺失时降级为直地平线并在结果中标注。
4. **PVGIS 方位角区间为 −180°~180°**，代码统一归一到 0°~360°。
5. **未评估置信度**：`confidence.py` 已就绪，但尚未接入 Open-Meteo 集合接口（为省流量默认不取）。
6. **Open-Meteo 免费层禁止商用**，正式商用需付费订阅。
7. **U 型说明**：蓝调窗口时长在低纬很短（赤道春秋分约 8 分钟），高纬夏季可达半小时以上，产品上需要区别对待。
